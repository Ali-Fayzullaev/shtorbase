## 1. Заказы — что уже работает

## 2. Оплата — новый функционал

**User story:** как менеджер, я хочу видеть с первого взгляда, оплачен заказ или нет, и не мог случайно выдать неоплаченный заказ.

### 2.1. Новые поля заказа

| Поле | Тип | Правило |
|---|---|---|
| `payment_status` | enum: `unpaid` / `partial` / `paid` | обязательное, по умолчанию `unpaid` |
| `paid_amount` | numeric(12,2) | ≥ 0, ≤ `total_amount` |
| `total_amount` | numeric(12,2) | уже есть, авто-расчёт триггером из `order_items` — не трогаем |

### 2.2. Правило синхронизации статуса

- `paid_amount = 0` → `unpaid`
- `0 < paid_amount < total_amount` → `partial`
- `paid_amount ≥ total_amount` → `paid`

Реализуется триггером в БД (см. [07-supabase-changes.md](./07-supabase-changes.md), шаг 1) — фронтенду достаточно передать `paid_amount`, статус выставится сам.

### 2.3. Визуализация (обязательно)

| Статус оплаты | Цвет бейджа |
|---|---|
| Не оплачено | красный `bg-red-50 text-red-600 border-red-200` |
| Частично (X%) | янтарный `bg-amber-50 text-amber-700 border-amber-200`, показывать процент оплаты |
| Полностью оплачено | зелёный `bg-emerald-50 text-emerald-700 border-emerald-200` |

Бейдж показывается: в списке заказов (колонка/карточка), в карточке заказа рядом со статусом, в форме создания/редактирования.

### 2.4. Бизнес-правило блокировки выдачи

Смена статуса на «Выдан» (`delivered`) при `payment_status !== 'paid'` требует явного подтверждения менеджера — диалог: «Заказ оплачен не полностью (X ₸ из Y ₸). Всё равно выдать?» → Отмена / Всё равно выдать.

### 2.5. Где редактировать оплату

- При создании заказа (`OrderForm`) — необязательное поле «Оплачено сейчас» (сумма), по умолчанию 0.
- В карточке заказа (`OrderDetail`) — отдельный блок «Оплата» с текущей суммой, кнопкой «Изменить», доступен только `manager`/`admin`.

### 2.6. Server Action

```
updateOrderPayment(orderId: string, paidAmount: number): Promise<{ error?: string; success?: boolean }>
```
- Роли: `manager`, `admin`.
- Валидация: `0 <= paidAmount <= order.total_amount`.
- Пишет запись в `order_history` (action: `payment_update`, old_value/new_value — суммы).

## 3. Индивидуальные параметры позиции заказа

**Проблема:** размеры (ширина/высота), точный оттенок ткани и подобные детали почти всегда индивидуальны под конкретного клиента — их нельзя зафиксировать в карточке товара один раз, они разные в каждом заказе. Сейчас у позиции заказа (`order_items`) есть только количество, цена и свободный текст `note` — структурированных параметров нет.

### 3.1. Решение

Добавить `custom_attributes` (jsonb) в `order_items` — пары ключ/значение, вводимые менеджером при добавлении позиции в заказ. Пример:

```json
{ "width_cm": 250, "height_cm": 180, "color": "бордо", "mechanism": "люверсы" }
```

Выбран простой `jsonb`, а не отдельная EAV-таблица — при 5 пользователях это быстрее в разработке, а строгая отчётность по атрибутам сейчас не нужна.

### 3.2. UI при добавлении позиции в заказ

После выбора товара в `OrderForm` — раскрывающийся блок «Параметры» с 2–4 полями ключ/значение (можно предзаполнить подсказками из `custom_fields` товара, если они заведены — см. [03-products-attributes.md](./03-products-attributes.md)). Не обязательное поле, можно оставить пустым и писать всё в общий `note`, как сейчас.

### 3.3. Отображение

- В карточке заказа — под каждой позицией, компактным списком «Ширина: 250см · Высота: 180см · Цвет: бордо».
- В печатной версии заказа (`app/(app)/orders/[id]/print/page.tsx`) — обязательно, это то, что видит сотрудник производства на бумаге/планшете.
