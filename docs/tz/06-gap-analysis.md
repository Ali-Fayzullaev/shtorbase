# Гэп-анализ: что уже есть в ShtorBase, что меняется, что новое

← [Назад к обзору](./00-overview.md)

## 1. Уже реализовано — переиспользуется как есть

| Компонент | Где в коде |
|---|---|
| Роли admin/manager/employee, инвайты, деактивация | `lib/actions/users.ts`, `lib/actions/invite.ts` |
| Заказы: создание, позиции, клиенты | `lib/actions/orders.ts`, `supabase/migrations/011_orders_and_clients.sql` |
| Настраиваемые статусы заказа (5 шт., без изменения кода) | `012_order_statuses.sql` |
| Автоматический пересчёт суммы заказа | триггер `trg_order_items_total` |
| Списание/возврат остатков при создании/отмене заказа | `deductStock`/`restoreStock` в `orders.ts` |
| История изменений заказа (аудит) | `014_order_history_deadline.sql`, `logOrderHistory` |
| Уведомления in-app + Telegram | `015_notifications.sql`, `lib/telegram.ts` |
| Дедлайн заказа | поле `deadline` |
| Динамические атрибуты товара (базовый уровень) | `custom_fields` / `product_custom_values`, `010_units_and_custom_fields.sql` |
| Гибкие единицы измерения | таблица `units` |
| Доска/список заказов, фильтры, статус-дропдаун с порталом | `components/orders/orders-table.tsx` |

**Вывод:** производственный воркфлоу и уведомления — это не новая система, а достройка уже работающего модуля заказов.

## 2. Требует изменения существующей логики

| Компонент | Сейчас | Нужно | Файл-ТЗ |
|---|---|---|---|
| `updateOrderStatus` | Полностью запрещает `employee` менять статус | Разрешить узкие переходы через новые `acceptOrder`/`completeOrder` | [02-production.md](./02-production.md) |
| Уведомление о готовности | Уходит `assigned_to` при любой смене статуса | Должно уходить менеджеру/создателю, когда статус становится `ready` | [04-notifications.md](./04-notifications.md) |
| `custom_fields` | Общие для всех товаров | Добавить `category_id`, чтобы у разных типов штор были разные наборы полей | [03-products-attributes.md](./03-products-attributes.md) |
| `getOrders` (список для employee) | Показывает только «свои» заказы | Добавить отдельную выборку «общая очередь» (`status='new' AND assigned_to IS NULL`) | [02-production.md](./02-production.md) |

## 3. Полностью новое — отсутствует в проекте

| Компонент | Почему нужно | Файл-ТЗ |
|---|---|---|
| `payment_status` / `paid_amount` на заказе | Сейчас есть только `total_amount`; статус оплаты в БД не хранится вообще | [01-orders-payments.md](./01-orders-payments.md) |
| `custom_attributes` (jsonb) на позиции заказа | Индивидуальные размеры/цвет клиента сейчас негде хранить структурированно — только общий текст `note` | [01-orders-payments.md](./01-orders-payments.md) |
| `variant_group_id` на товаре | Вариаций товара как понятия в схеме нет | [03-products-attributes.md](./03-products-attributes.md) |
| Экран «Общая очередь» с кнопкой «Принять» | Сейчас исполнитель либо назначается менеджером, либо равен создателю в «быстром заказе» — сценария «взять из общей очереди» нет | [02-production.md](./02-production.md) |

## 4. Итог

Из 6 модулей исходного запроса (Заказы, Товары, Производство, Пользователи, Оплата, Уведомления):
- **Готовы полностью:** Пользователи, базовые Заказы.
- **Требуют точечных доработок:** Производство, Товары, Уведомления.
- **Отсутствует полностью:** Оплата.

Это существенно меньший объём работы, чем разработка CRM/ERP с нуля — 6–7 миграций и 3–4 новых Server Action поверх существующей архитектуры (Next.js Server Actions + Supabase, без смены стека).
