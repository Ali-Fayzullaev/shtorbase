# Модуль «Товары» — типы, динамические атрибуты, вариации

← [Назад к обзору](./00-overview.md)

> **Статус: ✅ реализовано** — атрибуты по категориям (`custom_fields.category_id`) и вариации товара (`products.variant_group_id`, страница `/products/new?variant_of=<id>`, блок «Другие варианты» в карточке товара).

## 1. Типы товаров

Обычные шторы, рулонные шторы, умные шторы, карнизы, комплектующие/фурнитура — реализуются через существующую таблицу `categories`. Изменений кода не требует, только заполнение справочника новыми категориями (админ уже может это делать через настройки).

## 2. Динамические атрибуты — что уже есть

Механизм `custom_fields` + `product_custom_values` (типы `text`/`number`/`select`) уже реализован и позволяет добавлять новые поля без изменения кода — цвет, ткань, тип механизма и т.д.

## 3. Проблема: атрибуты сейчас общие для всех категорий

`custom_fields` не привязаны к категории — поле «Мощность мотора» будет показываться и у обычных штор, где оно бессмысленно. Для умных штор нужны свои поля (тип управления, мощность), для тканевых — свои (плотность, состав).

### 3.1. Решение
Добавить `category_id` (nullable) в `custom_fields`:
- `category_id IS NULL` → поле общее, показывается у всех товаров (обратная совместимость с уже заведёнными полями).
- `category_id = X` → поле показывается только у товаров категории X.

SQL — см. [07-supabase-changes.md](./07-supabase-changes.md), шаг 5.

### 3.2. UI

- В настройках атрибутов (`components/settings/...`, где сейчас управляют `custom_fields`) добавить выбор категории (селект «Применяется к: Все категории / [конкретная категория]»).
- В форме товара (`products/new`, `products/[id]/edit`) — фильтровать список показываемых кастомных полей по `category_id` товара (или показывать общие + под категорию).

## 4. Вариации товара (variants)

**User story:** как менеджер, я хочу завести одну штору «Венеция» в трёх цветах, не создавая с нуля три несвязанных товара с разными артикулами.

### 4.1. Подход для MVP

Полноценная EAV-модель вариаций избыточна для каталога такого размера (5 пользователей, умеренный ассортимент). Вместо неё — лёгкая связка:

- Каждая вариация — обычная запись в `products` со своим SKU (как сейчас).
- Добавляется поле `variant_group_id` (uuid, self-reference) — товары с одинаковым `variant_group_id` считаются вариациями друг друга.
- В карточке товара — блок «Другие варианты» со ссылками на товары с тем же `variant_group_id`.

SQL — см. [07-supabase-changes.md](./07-supabase-changes.md), шаг 6.

### 4.2. UI

- В форме товара — кнопка «Добавить вариацию» на странице уже созданного товара: открывает форму нового товара с предзаполненными общими полями (категория, часть атрибутов) и уже проставленным `variant_group_id` = id текущего товара (или id группы, если текущий товар уже в группе).
- В карточке товара в каталоге — маленькие цветные точки/чипы «Ещё N вариантов» под названием, клик — переход к другому варианту.
