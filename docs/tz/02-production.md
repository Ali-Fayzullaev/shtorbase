# Модуль «Производство» — очередь заказов и самообслуживание сотрудников

← [Назад к обзору](./00-overview.md)

> **Статус: ✅ реализовано** — `acceptOrder`/`completeOrder` в `lib/actions/orders.ts`, доска для сотрудника `components/orders/employee-order-board.tsx`. Не требует Supabase-миграции.

## 1. Проблема сейчас

Сегодня в коде (`lib/actions/orders.ts::updateOrderStatus`) стоит жёсткая блокировка:

```ts
if (role === 'employee') {
  return { error: 'Только менеджер или админ может изменять статус заказа' }
}
```

Это значит, что сотрудник производства физически не может сам взять заказ в работу или отметить его готовым — только менеджер меняет статусы за него. По ТЗ требуется обратное: сотрудник сам управляет своей частью цикла.

## 2. Целевой процесс

| Экран | Кто видит | Действие |
|---|---|---|
| «Новые» (общая очередь) | Все сотрудники | Кнопка **«✅ Принять заказ»** |
| «В работе у меня» | Сотрудник (свои), менеджер/админ (все) | Кнопка **«Готово»** |
| «Готовы» | Менеджер, админ | Только просмотр + связаться с клиентом |

## 3. Бизнес-правила

- **Принять заказ** может любой сотрудник — но только один. Как только заказ принят, он пропадает из общей очереди у остальных двоих.
- **Условие для приёма:** `status = 'new'` и `assigned_to is null`. Если менеджер уже назначил заказ конкретному человеку вручную — в общей очереди у остальных сотрудников такой заказ не отображается вовсе.
- **Отметить «Готово»** может только тот, кто принял заказ (`assigned_to = я`), либо менеджер/админ.
- Менеджер/админ в любой момент могут переназначить заказ или вернуть его в «Новый» (текущий функционал `assignOrder` не меняется).
- Каждый переход обязательно пишется в `order_history` — как уже реализовано для остальных смен статуса.

## 4. Новые Server Actions

### `acceptOrder(orderId: string)`
- Роли: `employee`, `manager`, `admin`.
- Проверка: заказ существует, `status === 'new'`, `assigned_to === null` (для `employee`; менеджер/админ могут поверх этого использовать обычный `assignOrder`).
- Действие: `assigned_to = user.id`, `status = 'in_progress'`.
- Пишет в `order_history` (action: `accepted`).
- Уведомление менеджеру/создателю заказа — см. [04-notifications.md](./04-notifications.md).

### `completeOrder(orderId: string)`
- Роли: `employee` (только если `assigned_to === user.id`), `manager`, `admin`.
- Проверка: `status === 'in_progress'`.
- Действие: `status = 'ready'`.
- Пишет в `order_history` (action: `status_change`, как обычная смена статуса).
- Уведомление менеджеру — см. [04-notifications.md](./04-notifications.md).

### Изменение в `updateOrderStatus`
Остаётся закрытым для `employee` для всех переходов, КРОМЕ тех, что покрыты `acceptOrder`/`completeOrder`. Переходы в `delivered`/`cancelled` — по-прежнему только менеджер/админ.

## 5. UI

### 5.1. Список заказов для сотрудника
`OrdersTable`/список на `/orders` для роли `employee` уже показывает только «свои» заказы (`assigned.eq.userId OR created_by.eq.userId` в `getOrders`). Нужно расширить: сотрудник также должен видеть отдельную вкладку/секцию **«Общая очередь»** — заказы `status = 'new' AND assigned_to IS NULL`, доступные всем.

Предлагаемая структура страницы `/orders` для `employee`:
1. Блок «Новые в очереди» — карточки с крупной кнопкой «Принять заказ».
2. Блок «Мои в работе» — карточки с крупной кнопкой «Готово».
3. Блок «Мои готовые/завершённые» — только просмотр.
