## 0. Быстрый контекст проекта

**ШторБаза** (shtorbase) — внутренняя веб-платформа для компании по производству и продаже штор (обычных и умных). Пользователей всего 5: 1 админ, 1 менеджер, 3 сотрудника производства.

Стек: Next.js 16 (App Router, Turbopack) + React 19 + TypeScript + Tailwind CSS 4 + Supabase (Postgres + Auth + Storage), мутации — через Next.js Server Actions (`lib/actions/*.ts`), не REST. Хостинг — Netlify, **автодеплой на каждый push в `main`**. GitHub: `Ali-Fayzullaev/shtorbase`.

Документация:

### 1.4. Индивидуальные параметры позиции заказа
**Миграция:** `supabase/migrations/020_order_item_attributes.sql` — `order_items.custom_attributes jsonb default '{}'`.

Менеджер при добавлении товара в заказ может указать произвольные пары параметр/значение (ширина, высота, цвет и т.д.) — раньше такого структурированного места не было, только общий текст `note`. Это аналог Shopify line item properties — намеренно НЕ часть карточки товара, потому что размеры почти всегда уникальны под конкретный заказ.

- `lib/actions/orders.ts` — `OrderItemSchema` принимает `custom_attributes`.
- `components/orders/order-form.tsx` — под каждой позицией мини-редактор пар ключ/значение («+ Параметр»).
- `components/orders/order-detail.tsx`, `print-order-view.tsx` — отображение.

### 1.5. Атрибуты товара по категориям
**Миграция:** `supabase/migrations/021_custom_fields_category_scope.sql` — `custom_fields.category_id` (nullable FK на `categories`, `null` = поле общее для всех).

Раньше все `custom_fields` показывались у всех товаров без разбора. Теперь можно привязать поле к категории (например, «Тип управления» только у умных штор).

- `lib/actions/settings-data.ts` — `createCustomField`/`updateCustomField` принимают `categoryId`.
- `components/settings/custom-fields-manager.tsx` — селект «Применяется к», требует проп `categories`.
- `components/settings/settings-tabs.tsx` — прокидывает `categories`.
- `components/products/product-form.tsx` — `visibleCustomFields` фильтруется по выбранной категории товара.

### 1.6. Вариации товара (первая версия — ручная)
**Миграция:** `supabase/migrations/022_product_variants.sql` — `products.variant_group_id uuid` + индекс.

Товары объединяются в группу вариаций через общий `variant_group_id` (НЕ полноценная EAV-модель — осознанно, для каталога такого размера это избыточно).

- `components/products/product-variants.tsx` — новый компонент, блок «Другие варианты» в карточке товара + кнопка «Добавить вариацию».
- `app/(app)/catalog/[id]/page.tsx` — показывает этот блок.
- `app/(app)/products/new/page.tsx` — принимает `?variant_of=<id>`, предзаполняет категорию/единицу измерения из исходного товара.
- `lib/actions/products.ts` — `getProductVariants(groupId, excludeId)`.

Этот способ («Добавить вариацию» = вручную создать один товар с предзаполненными полями) **остался в проекте** — им удобно дозаводить один новый вариант позже.

### 1.7. Артикул необязателен + массовое создание вариаций по значениям
**Миграций нет.**

Перед этим шагом было явное исследование через WebSearch (см. п. 2 ниже — «Обоснование дизайна»), по итогам которого:

- **Артикул (SKU) стал необязательным.** `ProductSchema.sku` в `lib/actions/product-mutations.ts` — `z.string().max(50).refine(v => v.length === 0 || v.length >= 2, ...)`. Если пусто — сервер генерирует `AUTO-XXXXXXXX` (функция `generateSku()`), с ретраем при редкой коллизии.
- **Массовое создание вариаций.** В форме добавления товара (`product-form.tsx`) появился необязательный шаг «Вариации»: менеджер вводит параметр («Цвет») и значения через запятую («Красный, Синий, Зелёный»). При сохранении вместо одного товара создаётся N — по одному на каждую комбинацию значений всех указанных параметров (декартово произведение). Каждый параметр вариации автоматически заводится (или переиспользуется) как обычное `custom_field`, отсканированное по категории (из п. 1.5) — то есть «Цвет: Красный» видно в карточке как любая другая характеристика, без отдельного скрытого механизма данных.

### 1.8. Живой прогресс создания вариаций
**Миграций нет.**

Изначально массовое создание было одним циклом на сервере (один Server Action, один HTTP round-trip) — с точки зрения UI это был просто спиннер без обратной связи. Пользователь попросил показать прогресс с именами. Переделано на **клиент-driven цикл**:

- `lib/actions/product-mutations.ts` разбит на:
  - `prepareVariantFields(categoryId, options)` — один раз находит/создаёт `custom_fields` под параметры вариации, возвращает `{ name: fieldId }`.
  - `createOneVariantAction(input)` — создаёт **ровно одну** карточку товара (используется общий `insertProductRow()` хелпер с ретраем SKU).
  - `insertProductRow()` — общий хелпер вставки с ретраем на коллизию SKU, теперь переиспользуется и обычным созданием, и вариациями.
- `components/products/product-form.tsx` — при наличии заполненных вариаций форма перехватывает сабмит (`onSubmit` + `e.preventDefault()`, обычный путь без вариаций продолжает работать через нативный `action={formAction}` как раньше), сама вызывает `prepareVariantFields`, затем в цикле `for` вызывает `createOneVariantAction` на каждую комбинацию, обновляя state `batchProgress` после каждого шага. Модальное окно показывает прогресс-бар, имя текущей создаваемой карточки («Штора «Венеция» — Красный», 2 из 5), и финальный экран «Готово!» перед `router.push('/catalog')`.
- `app/globals.css` — добавлен keyframe `indeterminate-bar` / класс `.animate-indeterminate` для тонкой полосы прогресса на кнопке обычного (не вариантного) сохранения.

## 2. Обоснование дизайна (важно для следующего ИИ — не переизобретайте)

Перед шагом 1.7 был явный research через агента (WebSearch) по теме «как Shopify/WooCommerce моделируют товары с вариациями, что путает персонал/клиентов». Ключевые выводы, которые заложены в архитектуру:

1. **Опции vs варианты vs спеки.** Shopify: продукт имеет «options» (Цвет, Размер), система сама строит «variants» — декартово произведение. WooCommerce: «attributes» (описательные) vs «variations» (то, что реально хранится/стоит денег). У нас: `custom_fields` = спеки (описательная информация), а параметр вариации при массовом создании товара одновременно становится и `custom_field`, и осью для генерации отдельных карточек — переиспользование существующего механизма вместо новой EAV-таблицы.
2. **SKU не обязателен нигде** — ни в Shopify, ни в WooCommerce. Обязательность SKU создаёт лишнюю работу без пользы для внутреннего инструмента на 5 человек. Отсюда — автогенерация.
3. **Made-to-order паттерн (кастомные размеры под заказ)** — Shopify называет это «line item properties»: данные, привязанные к позиции заказа, а не к товару, потому что не участвуют в остатках/цене каталога. У нас это `order_items.custom_attributes` (п. 1.4) — сделано даже до того, как я нашёл этот термин в исследовании, архитектура совпала независимо.
4. Пользователь явно выбрал (через `AskUserQuestion`) вариант **«автогенерация вариаций из списка значений»** вместо «оставить как в шаге 1.6 (вручную по одной)» — это было прямое решение пользователя, не моё предположение.

## 4. Известные ограничения / что осознанно не сделано

- **Фото не клонируются при массовом создании вариаций.** Каждая созданная карточка стартует без изображений — менеджер добавляет их по каждой отдельно. Решение было явным (см. коммит `1c42f26`), чтобы не усложнять первую версию (загрузка файлов в Storage N раз в цикле — отдельная задача).
- **Лимит на массовое создание — 60 комбинаций** (`combos.length > 60` → ошибка). Проверка стоит и на клиенте (в `product-form.tsx`), и раньше стояла на сервере (сейчас там же, в `handleFormSubmit`, серверная часть больше не валидирует лимит — если решите разрешить конкурентные/параллельные создания или другой источник вызова `createOneVariantAction`, стоит вернуть проверку и на сервер).
- **Вариации второго уровня (Цвет × Размер и т.д.)** поддержаны кодом (декартово произведение по всем указанным параметрам), но не были протестированы вручную в браузере — только `tsc`/`lint`/`build`. Стоит проверить в реальном UI перед тем, как считать фичу полностью законченной.
- **Полноценный ручной браузерный прогон новых экранов не проводился** в этой сессии (не было доступа к рабочему Supabase-инстансу с прогнанными миграциями) — вся проверка была на уровне `npx tsc --noEmit`, `npm run lint`, `npm run build`. Рекомендация следующему агенту/разработчику: пройти вручную (или через `/run`) сценарии — приём заказа сотрудником, оплата, создание вариаций — на реальных данных.

## 5. Полезные команды / факты о репозитории

- `npm run build` — с Turbopack, ~25–30 сек компиляция. На этой машине без `.env` заполненного полностью падает на этапе сбора данных страниц (`Missing CLOUDINARY_CLOUD_NAME`) — это ожидаемо локально, не признак сломанного кода, если сама компиляция и `Running TypeScript` прошли успешно.
- `npm run lint` — в проекте **уже есть 8 ошибок и ~21 предупреждение до этой сессии** (не мои): `components/theme/theme-provider.tsx:44`, `components/users/invite-form.tsx:14`, `components/orders/orders-table.tsx:291` (все три — `react-hooks/set-state-in-effect`), `lib/actions/orders.ts:160,197` (`prefer-const` на `profileMap`), плюс несколько `no-unused-vars`. **Это baseline, не трогать/не чинить, если явно не попросят** — при каждой проверке в этой сессии число ошибок сверялось и оставалось тем же (не росло).
- **Netlify автодеплоит `main` при каждом push.** Каждый коммит в этой сессии — это уже прод-деплой (если у пользователя настроен CI/CD от push, а он настроен, судя по `netlify.toml`).
- Package manager — npm, `package-lock.json` в репозитории. Осторожно: `npm install` на этой Windows-машине слегка меняет `package-lock.json` (убирает поле `libc` у нескольких optional-зависимостей) — это шум от версии npm, не реальное изменение зависимостей, откатывайте (`git checkout -- package-lock.json`) перед коммитом, если увидите такой дифф.

## 6. Сессия 10.08.2026 — проверка хендоффа + security fix

Пришёл следующий агент, прочитал этот файл, проверил пункт 3.1 напрямую через Supabase MCP (project `jzatuomwxnzsiuanbdom`).

- **Миграции 019–022 подтверждены применёнными в проде** (колонки `payment_status`/`paid_amount`/`custom_attributes`/`category_id`/`variant_group_id` реально существуют в БД). Пункт 3.1 из раздела 3 закрыт, статусы в `docs/tz/07-supabase-changes.md` обновлены на ✅.
- `.env.local` полностью заполнен, включая `CLOUDINARY_CLOUD_NAME` — проблема из п. 3.2 больше не актуальна на этой машине.
- **Найдена и закрыта брешь безопасности**, не связанная с сессией 9–10.08: Supabase security advisor (`rls_disabled`, critical) показал, что таблицы `notifications` и `order_history` с момента своего создания (миграции 014, 015) не имели RLS вообще — были полностью открыты на чтение/запись через anon/authenticated Supabase-клиент, в обход Server Actions. Так как весь код всегда обращается к этим таблицам через `createAdminClient()` (service-role, RLS не касается), закрытие бреши **не могло сломать приложение** — только убрало прямой доступ через публичный anon key.
  - Миграция `supabase/migrations/023_rls_notifications_order_history.sql`, применена напрямую в проде через MCP (`apply_migration`), подтверждена через `get_advisors` — критичный `rls_disabled` пропал.
  - Политики: `notifications` — читает/обновляет только свои строки (`user_id = auth.uid()`), админ читает все; `order_history` — insert только от своего имени, select — свои записи + `manager`/`admin` видят всё, update/delete запрещены явным `revoke` (как у `audit_log`).
  - Задокументировано как «Шаг 7» в `docs/tz/07-supabase-changes.md`.
- Остались фоновые (не critical) security-warnings от advisor, не трогались: `function_search_path_mutable` на нескольких функциях, `pg_trgm` в public-схеме, security-definer функции исполняемы anon/authenticated, отключена HaveIBeenPwned-проверка паролей. Не входило в задачу, не факт что стоит чинить для внутреннего инструмента на 5 человек — решать пользователю.
- **Файл миграции 023 создан локально, но ещё не закоммичен** — следующему агенту/пользователю нужно решить, коммитить ли его (миграция уже накатана на прод-БД напрямую через MCP, так что коммит нужен только для истории репозитория, не для функциональности).
- Пункты 3.2 (браузерный прогон вариаций 2-го уровня, ручное тестирование новых экранов) остаются открытыми — до них в этой сессии не дошли, приоритет был отдан security-фиксу по явному выбору пользователя.
